# Design

## Context

- 定位文档已部分对齐(战略摘要章节已采用演进方案语言),遗留:指向 `../research/` 的失效链接(目录已移至 `docs/refactor/`)、缺交付边界/部署模式与消费者契约章节、竞品矩阵中与既定定位矛盾的表述。`architecture.md`(:7—141)按十个模块组织,无控制面/执行接入层/信任边界与七能力域内容。ADR 已有 001—033(INDEX 计数已过期)。
- 清单工具现状(#194 之后):`extract` 按 ID 合并、矛盾显式失败、幂等;`check` 含矛盾检测与 `--strict`(全部 WARNING 变失败);CI 尚未接入清单校验;YAML `schema: 1`,347 条目,字段所有权已在头注释成文。
- `docs/design/writing-style.md`:定位/架构文档不得含描述性数字与日期(`docs/features/`、`docs/design/adr/` 豁免)——架构补充与定位章节写作时适用;catalog 的 P1—P5 标签属项目内部 ID,不受限。

## Goals / Non-Goals

**Goals**

- 定位/架构/ADR/catalog/roadmap 五类文档与既定方案一致,历史实现事实不丢失。
- 清单 schema v2 落地,新/变更条目强制治理字段,历史欠账显式化。
- catalog/roadmap 的清单派生内容改为受管生成,漂移机器可检。
- CI 接入清单校验(非严格为门,严格模式按增量规则启用)。

**Non-Goals**

- 不做竞品对照全面重调研(定位矩阵仅做一致性修订,证据复核另行安排)。
- 不为 347 条历史条目一次性补齐治理字段(显式欠账机制承接)。
- 不移动任何源码目录、不创建 `hecate-runtime`/`hecate-runner` 包(ADR-035 只批准方向,实施归 step5b)。
- 不重写 `architecture.md` 的既有模块清单(增量补充)。

## Decisions

### D1: 两份 ADR,编号实施时取号不预占

第一份"平台治理语义与执行后端地位"打包六个决策(核心职责=治理结果保证、内置 Runtime 为参考实现、托管 harness×环境双轴登记、事件/会话所有权、能力协商、不承诺无损状态迁移)——它们在方案 §一/§二已成文且互为前提,一份 ADR 便于整体引用与废止。第二份"独立执行组件的包名与目录迁移方向"单独成文,因为它有独立的实施时点(step5b)与可废止生命周期,混入第一份会迫使两者同步变更。编号遵循方案"按 ADR 索引分配编号,不预占":实施时按 INDEX 取下一空闲号(当前序列尾部 033);若被并行工作流占用则顺延。INDEX.md 顺带修正过期计数(用不含数字的表述)。

*备选*:每决策一份 ADR(6 份)。否决——决策间强耦合,拆散后单份 ADR 无法独立成立;方案原文亦以"一份 ADR"措辞。

### D2: schema 2 一次性引入,字段可空、欠账显式

新增 7 个治理字段 + 3 个研究类字段(见 spec)。设计要点:① 字段可空/可显式 `n/a`,校验器区分"缺失(欠账)"与"显式不适用(通过)";② 不做 347 条目的批量回填——由受管生成与欠账报告逐步收敛;③ `maturity` 与 `status` 解耦在校验器中落实(delivered 不推导 production);④ schema 版本号用于工具拒绝误用旧语义,而非触发迁移脚本。研究类字段只对研究/实验状态条目强制,避免给 delivered 条目塞不适用字段。

*备选*:按能力域分批引入字段(schema 1.1/1.2)。否决——枚举校验与严格规则需要单一版本语义,分批会让 CI 规则随 schema 版本漂移。

### D3: 受管生成用显式区域标记,迁移期逐字段报告

catalog/roadmap 中由清单派生的表格(统计块、处置分类表、里程碑表)用成对 HTML 注释标记界定(如 `<!-- feature-inventory:managed:catalog:dispositions begin/end -->`)。生成器只写标记内内容;校验器重新生成并与当前文件比对,差异报告到"条目 ID + 字段"。迁移路径:先为受管表格加标记并登记为"报告不失败",本 change 完成内容搬迁后翻转为"漂移即失败"——翻转开关由标记属性(`strict="true"`)表达,不引入第二套配置。

*备选*:整文件生成(catalog 全量由 YAML 生成)。否决——catalog 承载大量叙事正文,全量生成会消灭手写内容;方案也要求"Markdown 拥有说明性正文"。

### D4: catalog 重排方法——处置标签映射,历史不删除

按方案 §六的三张映射表(已实现能力边界复核、提前并纳入核心、保留转后端、移出核心)逐行落为 catalog 条目的处置标注与新增验收条目;全部现有 ID 保留,新条目用未占用后缀(实施时以清单 ID 集合核对)。对应清单条目(边界复核的十项能力 + §六新增映射)同步填 schema v2 治理字段;其余条目维持欠账。三类新增登记表(七类治理能力五元组、五能力契约登记、七能力域覆盖)以受管区域落 catalog/roadmap,数据源为清单或显式登记表,统一在内容搬迁完成后翻转 strict(任务 5.11)。roadmap 以方案 §七的迭代表(I-A…I-H)与里程碑表(M-S…M-R)替换"未来排期",Sprint 1—10 归入"历史排期(已完成)"章节,不删除。

### D5: 消费者契约用中性表述

定位文档的消费者契约章节以"业务 App 私有化交付(示例:结构化库存类业务)"表述,登记技术预览/独立生产/受管生产三级门槛与 HTTP/JSON 首入口;不出现具体业务名称,不把示例业务写入平台模型——与 SC 场景组的"示例业务域"口径一致。

### D6: 三个 PR 拆分

PR1 文档:positioning + architecture + ADR-034/035 + INDEX(纯文档,可先行评审)。PR2 清单工具:schema v2 字段/校验器/欠账与严格规则 + 测试(不改文档)。PR3 生成与重排:受管标记/生成器/漂移检测 + catalog/roadmap 内容搬迁 + CI 接线。PR2 先于 PR3(生成器依赖 schema v2 字段定义);PR1 与 PR2 无依赖可并行。

## Risks / Trade-offs

- [catalog 重排漏掉 §六某行导致映射不完整] → 任务清单按 §六表格逐行列出(每行一个任务勾选项),评审对照方案原文;清单 ID 集合由 check 的重复/漂移检测兜底。
- [受管标记引入期间 check 误报漂移] → 标记初始 `strict="false"`,漂移只报告;内容搬迁完成的 PR 中翻转为 true,翻转时同一 PR 内必须全绿。
- [枚举取值未来不够用] → 枚举扩展走 spec 修订(本能力),不做开放字符串;`superseded_by` 等自由文本字段承接未列举差异。
- [定位矩阵一致性修订引入新的未经核验竞品声明] → 修订只删除/弱化与新定位矛盾的表述,不新增竞品事实;新增事实须带官方来源并登记到 References,否则不写。

## Migration Plan

纯文档 + 工具:三个 PR 依序合入即生效,无部署/回滚动作;PR 级回退 = revert。清单 schema 2 生效后旧 schema 1 文件不再产出(extract 固定写 2),已合入的 schema 1 状态由同 PR 的全量重写迁移(字段缺失即欠账,无损)。CI 接线先以非严格模式运行一个观察期(与欠账报告并行),由维护者在欠账收敛后切严格——切严格不阻塞本 change 归档,作为遗留任务显式登记。
