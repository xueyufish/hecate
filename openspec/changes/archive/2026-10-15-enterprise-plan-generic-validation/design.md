# Design

## Context

见 proposal.md。当前方案的使用方式、信任规则、独立消费依据、step7/9/16、功能目录映射、迭代顺序和末尾决策均包含行业前提；仅删开头段落会留下相互矛盾的要求。step1 的库存 fixture 和 SC 验收名称已有历史实现与机器清单引用。

## Goals / Non-Goals

**Goals:** 在同一方案内统一通用任务、近期受管闭环目标和独立交付边界；把已有证据与未来通用场景的验收明确区分。

**Non-Goals:** 不改动运行行为、正式能力 spec 或其他规划文件；不将通用场景描述视为新测试已交付，不重编号或翻转状态。

## Decisions

- 移除当前产品要求中的行业名称，将库存读写约束泛化为业务资源/API 约束；不全局替换 `App`，该词仍表示有效的通用客户端形态。
- 保留 step1 已完成的模拟库存 API 事实及 SC 的既有验收名称，在场景说明处集中标明它们属于历史技术 fixture。相比重命名场景，此方式可保持 manifest、测试和历史报告的可追溯性。
- 通用任务采用“读取材料→生成工单草稿→人工审批→调用测试业务 API→核验结果”，同时记录预期产物、拒绝和对账；已有通过状态只适用于原证据范围。
- 近期交付以 M-A/I-Cb 的内置受管执行闭环为目标，保留 I-Ca 独立 profile 的完整退出条件。独立交付路径仍存在，I-Ca 不再因特定 App 被设为 I-Cb 的先决条件；共享治理和真实执行验收仍是各自前置。
- Runtime 独立消费以已交付 Runner 作为具名消费者依据，不以已经取消的行业需求证明扩展点必要性。
- step2 的关联文档同步仍保持未完成，并补充本次方向调整；不在此文档 change 中宣称其他规划已同步。

## Risks / Trade-offs

- [新目标被误读为已通过] → 保留所有历史勾选、技术交付状态、未完成门槛和报告引用。
- [历史 fixture 名称仍含库存] → 明确其证据角色与新需求脱钩，不修改测试或历史记录。
- [仅末尾调整优先级导致前文矛盾] → 同步使用方式、依赖说明、迭代段落和结尾定位，检查 I-Ca/I-Cb 引用。

## Migration Plan

仅文档修订，无部署或数据迁移。回退通过撤销文档 diff 完成。校验 diff、章节/状态、既有链接及 OpenSpec；产品测试无需重跑。
