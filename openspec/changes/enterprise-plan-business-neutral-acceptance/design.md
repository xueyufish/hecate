# Design

## Context

见 proposal.md 的 Why。现有执行规格已区分任务声明的输出 Schema、策略要求的审批与持久恢复；方案中的工单措辞不应扩张这些契约。

## Goals / Non-Goals

**Goals:** 方案按可观察的平台能力描述验收，明确条件适用与合成工具边界，供后续 change 引用。

**Non-Goals:** 不定义下一项开发的具体进程拓扑、Task/Run 续跑策略或测试实现，不改变现有能力与证据。

## Decisions

- 总体验收使用工具反馈、受控动作、结果校验、停止与对账等通用术语，业务规则仍归调用方或业务系统；不把特定工单流程作为平台产品责任。
- 将审批等待和进程重启列为指定能力场景，按任务定义、策略和支持的 profile 验收；不强制每个任务经历这些阶段。输出 Schema 仅对声明它的任务适用。
- 团队验收保留跨任务交接、worker 重启、幂等与撤权保证，移除工单对象约束。保留既有 fixture 及历史证据，避免改名造成证据断链。

## Risks / Trade-offs

- [过度抽象后无法判定验收] → 保留动作次数、回执、产物校验、权限及等待/恢复等可观察要求；具体输入、工具和断言由所属 change 明确。
- [被误读为新增认证已完成] → 保持步骤编号、状态、历史记录与默认开关不变；本次仅修订文档。
