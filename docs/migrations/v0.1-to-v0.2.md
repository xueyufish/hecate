# Migrating from Hecate 0.1.x (Alpha) to 0.2.x (Beta)

How to safely upgrade from an Alpha deployment to a Beta deployment of Hecate.

> **This document covers the 0.1 → 0.2 version upgrade.** For the general upgrade procedure (which applies to every version), see the [Upgrade Guide](../operations/upgrade-guide.md). For the schema migration pattern Hecate uses, see [Expand-Contract Migration Guide](expand-contract-guide.md).

---

## What's changing in 0.2

The 0.2 release is the **Beta exit** — the point at which Hecate commits to backwards compatibility for the 0.x line. Concretely:

| Area | 0.1.x (Alpha) | 0.2.x (Beta) |
|---|---|---|
| **API compatibility** | Breaking changes allowed at any time | Breaking changes only at minor version bump (0.x.0) |
| **Graph DSL schema** | Subject to change | Frozen at 0.2.0 GA; new fields may be added but old ones won't be renamed/removed |
| **OpenAI-compatible subset** | Best-effort | Documented and stable (chat, embeddings*, models — see below) |
| **CLI commands** | Subject to change | `hecate agent/workflow/kb/...` surface frozen |
| **Config schema (env vars)** | Subject to change | Documented; renames require migration note |
| **Database schema** | Subject to change | Backwards-compatible migrations (expand-contract) |
| **Plugin manifest** | Subject to change | `api_version` field required |

> **Note on embeddings**: `/v1/embeddings` is **not** a public Hecate endpoint. Embeddings are computed internally during knowledge base ingestion. See [Tutorial: OpenAI SDK Compatibility](../tutorials/10-openai-compatibility.md) for details.

## Pre-upgrade checklist

Before running the upgrade, verify each of these:

### 1. Confirm you can roll back

```bash
# Snapshot the current state
curl -X POST http://localhost:8000/api/backups \
  -H "Authorization: Bearer $ADMIN_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "backup_type": "full",
    "scope": "all",
    "storage_type": "minio",
    "storage_path": "s3://backups/pre-0.2-upgrade/",
    "description": "Pre-0.2 upgrade snapshot"
  }'

# Note the backup ID returned
```

### 2. Confirm Beta exit criteria are met

The  lists Beta exit criteria. The most relevant for this upgrade:

- [ ] You're on the latest 0.1.x patch (e.g., `0.1.12` before upgrading to `0.2.0`)
- [ ] You have reviewed the deprecation log for any APIs you depend on
- [ ] You have a tested backup restoration procedure (run a drill in the last 30 days)
- [ ] You have a maintenance window (Beta exit will require restart)

### 3. Capture current config

```bash
# Save env vars for diff comparison
hecate config show > /tmp/hecate-0.1-config.env

# Save current DB version
alembic current  # Should show the last 0.1.x migration
```

## Upgrade steps

### Step 1 — Pull the new image / code

```bash
# Docker Compose
docker compose pull
docker compose up -d --no-deps  # Don't restart dependents yet

# Kubernetes
helm repo update
helm upgrade hecate hecate/hecate --version 0.2.0
kubectl rollout status deployment/hecate --timeout=10m
```

### Step 2 — Run Alembic migrations

```bash
# Check what migrations will run
hecate-migrate plan 0.1.x 0.2.0

# Apply migrations
hecate-migrate upgrade head

# Verify
alembic current  # Should show the last 0.2.x migration
```

Schema migrations between 0.1 and 0.2 follow the **expand-contract pattern** (see [Expand-Contract Guide](expand-contract-guide.md)):

- **Expand**: add new column (nullable, no default)
- **Backfill**: populate from old column via `UPDATE ... SKIP LOCKED`
- **Switch**: deploy code that reads from new column
- **Contract**: drop old column (next minor version)

So in 0.2 you may see:
- New columns added (existing code ignores them)
- New tables created (existing code doesn't read them)
- Indices added (transparent)

You will **not** see in 0.2:
- Dropped columns (deferred to 0.3)
- Renamed columns (use expand-contract for column renames)
- Changed types (deferred to 0.3)

### Step 3 — Apply configuration changes

#### Renamed env vars

| Old (0.1.x) | New (0.2.x) | Action |
|---|---|---|
| `AGENT_STATE_STORE_BACKEND` | `SESSION_STATE_STORE_BACKEND` | Rename in `.env` |
| `HECATE_API_KEY` | `HECATE_API_KEYS` (now accepts comma-separated list) | Rename; add `S` if you had a single key |
| `SENTRY_DSN` | `OBSERVABILITY_SENTRY_DSN` | Rename |

Old names are still accepted in 0.2.0 with a deprecation warning logged on startup. Support will be removed in 0.3.0.

#### New required env vars

| Variable | Default | Required? |
|---|---|---|
| `STABILITY_COMMITMENT` | (none) | Recommended — set to `beta` for Beta deployments |

#### Removed env vars

None in 0.2 (everything is additive until 1.0).

### Step 4 — Restart Hecate

```bash
# Docker Compose
docker compose up -d

# Kubernetes
kubectl rollout restart deployment/hecate
kubectl rollout status deployment/hecate --timeout=5m

# Verify health
hecate preflight
curl http://localhost:8000/health  # Should return 200
```

### Step 5 — Run verification

```bash
# Smoke test the OpenAI-compatible endpoint
curl -X POST http://localhost:8000/v1/chat/completions \
  -H "Authorization: Bearer $HECATE_API_KEYS" \
  -H "Content-Type: application/json" \
  -d '{"model": "gpt-4o-mini", "messages": [{"role": "user", "content": "ping"}]}'

# Smoke test the Management API
curl http://localhost:8000/api/agents \
  -H "Authorization: Bearer $HECATE_API_KEYS"

# Smoke test the canvas
open http://localhost:3000  # Should show the workflow list
```

### Step 6 — Verify the audit trail

```bash
# Confirm the upgrade event was logged
curl "http://localhost:8000/api/audit/events?event_type=system.upgraded" \
  -H "Authorization: Bearer $ADMIN_KEY"
```

Expected:
```json
{
  "events": [
    {
      "event_type": "system.upgraded",
      "from_version": "0.1.x",
      "to_version": "0.2.0",
      "timestamp": "...",
      "actor_id": "system"
    }
  ]
}
```

## Plugin compatibility

If you have custom plugins:

### Manifest updates required

Add `api_version` to your manifest:

```python
# Before (0.1.x)
manifest = PluginManifest(
    type="evaluator",
    name="my_metric",
    version="1.0.0",
    description="...",
)

# After (0.2.x)
manifest = PluginManifest(
    type="evaluator",
    name="my_metric",
    version="1.0.0",
    api_version="1.0",          # ← NEW: required
    min_platform_version="0.2.0", # ← NEW: bump
    description="...",
)
```

Without `api_version`, your plugin will be rejected at load time with:

```
ERROR: Plugin 'my_metric' has no api_version. Update to api_version='1.0' for Hecate 0.2+.
```

### Code changes

Most plugins require **no code changes**. If your plugin:

- Uses `hecate.engine.*` internals → **may break** (check release notes)
- Implements an ABC from `hecate.plugin.spi.*` or `hecate.auth.provider` → **no change**
- Reads from `hecate.plugin.sdk.PluginContext` → **no change** (interface stable)

## API breaking changes in 0.2

This section will be populated as 0.2 development progresses. The current list (will be filled before 0.2 GA):

| Endpoint | Old (0.1.x) | New (0.2.x) | Migration |
|---|---|---|---|
| `POST /api/agents/{id}/export` | Returns object with `config` field | Returns object with `model_config` field | Rename `config` → `model_config` in consumers |
| `GET /api/agents/{id}` | Returns `workspace_id` as UUID string | Returns `workspace_id` as UUID string (no change) | None |
| `POST /api/workflows/import` | Accepts JSON | Accepts JSON (schema stricter; unknown keys rejected) | See [Graph DSL](../reference/graph-dsl.md) |

> **More entries will be added as Beta stabilizes.** Subscribe to [GitHub Releases](https://github.com/xueyufish/hecate/releases) for notifications.

## Database migration details

The 0.2 schema migrations include:

| Migration | Description | Reversible? |
|---|---|---|
| `add_workspace_member_role_check` | CHECK constraint on `workspace_members.role` enum | Yes |
| `add_agentcard_signing_keys` | New table for ES256 keypairs (when A2A signed cards enabled) | Yes (DROP TABLE) |
| `expand_audit_log_to_hash_chain` | Add `previous_hash` + `entry_hash` columns to `audit_logs` | Yes (DROP COLUMN) |
| `expand_backup_records_for_pitr` | Add `wal_position` + `incremental_chain` columns to `backup_records` | Yes |

All migrations are **expand-contract**: old code continues to work with the new schema, new code uses the new columns. The "contract" phase happens in a later 0.2.x or 0.3.0 release.

For deep dive on the migration pattern: [Expand-Contract Migration Guide](expand-contract-guide.md).

## Rollback procedure

If something goes wrong after the upgrade:

```bash
# 1. Stop Hecate
docker compose stop api   # or: kubectl scale deployment/hecate --replicas=0

# 2. Restore the pre-upgrade backup
hecate-migrate restore \
  --backup-id <PRE_UPGRADE_BACKUP_ID> \
  --component all

# 3. Downgrade the code (optional)
git checkout v0.1.x   # or: docker compose pull v0.1.x

# 4. Restart
docker compose up -d

# 5. Verify
hecate preflight
curl http://localhost:8000/health
```

**Rollback is supported** for the entire 0.2.x line as long as you have a backup from before the upgrade.
